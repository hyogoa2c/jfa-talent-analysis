# holdout gold 判定プロトコル（SAP v9 §6b-2b・§11 手順 2）

対象: `data/manual/gold_holdout_worksheet.csv`（539 件、盲検）。
判定者は 2 名で、**互いの回答を見ずに独立に**判定する。
記入先は `data/manual/gold_holdout_verdicts_rater_a.csv` / `_rater_b.csv`。

この 539 件は**独立 holdout** であり、分類規則の開発には一切使っていない。
判定が規則の出力に引きずられると holdout ではなくなるため、以下の盲検条件を守ること。

---

## 1. 判定すること

**その選手が最初のプロ契約を結ぶ直前に所属していた育成機関はどこか。**

判定者が答えるのは次の 2 つで、**カテゴリの最終確定は判定者の仕事ではない**。

1. `gold_final_institution` — 機関の正式名称（例: `ガンバ大阪ユース`、`静岡学園高等学校`、
   `筑波大学`、`三菱養和SCユース`）。**在籍年が分かれば `note` に併記する。**
2. `gold_pathway_category` — 下表の一次分類。

| 値 | 意味 |
|---|---|
| `j_club_academy` | クラブの下部組織（**育成年代 = U-18 以下**）が最終育成機関 |
| `high_school` | 高校が最終育成機関 |
| `university` | 大学（短大・専門学校を含まない。専門学校は `other` と `note`）が最終育成機関 |
| `other` | 海外クラブ、成人年代のチーム、その他上記に当てはまらない |
| `unknown` | 育成年代の所属が判明しない（`determination` も併せて後述の値にする） |

**クラブが J リーグ加盟だったかどうかは判定しなくてよい。** 加盟年は版管理された名簿
（`j_league_club_registry.csv`）でコーディネーターが機械的に当てる。判定者は
「三菱養和SCユース」「横河武蔵野FCユース」のような非 J のクラブも `j_club_academy` と書き、
**機関名を正確に残す**ことに集中する。

### 判定規則（推測せず、この規則に従う）

- **原則**: 最初のプロ契約の直前に所属していた育成機関を採る。
- **J クラブ U-18 ユースと高校の同時在籍は「クラブ側」**（育成主体はアカデミー、高校は
  提携通学先）。手がかり: 「(クラブ)ユースからトップチームに昇格」、「○○ユース（△△高校）」の並記。
- **U-15 ジュニアユースのみを経て高校（クラブ籍なし）に進んだ場合は高校。**
  同時所属ではなく逐次移行だから。
- **成人年代のチーム（ネクスト／セカンド／アマチュア／サテライト等）は育成機関ではない。**
  その前の段階（大学・高校・ユース）を採る。前段階が分からなければ `unknown`。
- **2 種登録でプロ相当の出場をした後に大学へ進んだ場合**は、最初のプロ契約の前の段階を採る。
  判断がつかなければ `indeterminate` にして `note` に事実を書く（無理に倒さない）。
- **「最初のプロ契約」がいつかを詰めなくてよい**（v2 で明確化。両判定者が穴として指摘した）。
  問いは実質的に「**育成機関のうち最後に在籍したのはどこか**」である。育成機関とは
  クラブ下部組織（U-18 以下）・高校・大学の 3 つで、**その後に JFL・地域リーグ・企業チーム・
  海外の下位クラブ・アマチュアクラブを経ていても答えは変わらない**（それらは育成機関ではない）。
  例: 藤枝東高 → Honda FC → 湘南 は `high_school`。契約が J なのか JFL なのか、
  そもそもプロ契約だったのかを判定する必要はない。
- **専門学校は `other`** とし、`gold_final_institution` に正式名称を書く
  （例: JAPAN サッカーカレッジ、大原スポーツ専門学校）。大学ではない。
- **迷ったら倒さない。** 判定不能は失敗ではなく、率として報告される情報である。

## 2. 根拠の要件

- **Wikipedia は単独根拠にできない。** 本文もインフォボックスも不可。測定している側の情報源と
  編集過程を共有しており、独立検証にならないため。手がかりに使うのは構わないが、
  **必ず Wikipedia 以外で裏を取る**。裏が取れなければ `indeterminate`。
- **次も単独根拠にできない**（v2 で明記。パイロットで、規則の文言は満たすのに趣旨を外す
  ソースが実際に使われた）:
  - **Wikipedia のミラー・翻案**（kiddle.co、wikiwand.com など）——見た目は別サイトだが中身は Wikipedia
  - **出典を示さない人物アグリゲータ**（jitenon.jp、weblio.jp など）
  - **個人ブログ・SNS**（ameblo.jp、note.com、mixi.jp など）
  - **有志運営／利用者編集のデータベース**（fansaka.info、soccer-db.net、transfermarkt など）
  - **ファンサイト**

  これらしか見つからない場合の答えは「弱い根拠で `confirmed` にする」ではなく **`indeterminate`** である。
  判定不能率が高いこと自体は設計上織り込み済みで、**弱い根拠で埋めるほうが害が大きい**。
- 主根拠の優先順:
  1. クラブ公式サイトの選手ページ・入団リリース（`official_club`）
  2. リーグ・協会の公式データ（J リーグ、JFA、高体連、大学連盟）（`official_league`）
  3. 学校・アカデミーの公式サイト（`school`）
  4. 報道（ゲキサカ、スポーツ紙、地方紙）（`news`）
  5. その他（`other`。`note` に種別を書く）
- `evidence_url` は**その記述が実在するページの URL** を 1 件（複数なら `;` 区切り）。
- `evidence_quote` は**逐語引用が必須**。要約や言い換えではなく、経歴が読み取れる部分を
  原文のまま短く貼る（例: `選手歴：G大阪ジュニアユース-G大阪ユース-G大阪`）。
  **引用が書けない根拠は根拠として認めない。**
- `researched_at` は調査日（`YYYY-MM-DD`）。

## 3. `determination` の 3 値

| 値 | 意味 | 扱い |
|---|---|---|
| `confirmed` | 非 Wikipedia の根拠で機関を確定できた | 混同行列に入る |
| `indeterminate` | 本人には到達できたが育成年代の所属を確定できない | **繰り上げず保存**し、層別の判定不能率として報告 |
| `unreachable` | 本人に到達できない（記事・記録が存在しない、同名別人と区別できない） | 同一層の予備を `draw_order` 順に繰り上げる |

`indeterminate` と `unreachable` の違いは「**人物には届いたか**」である。
届いたが育成年代の記述がないのが `indeterminate`、そもそも人物を同定できないのが `unreachable`。

**同名別人に注意する。** ワークシートの `birth_date` と `senior_clubs` で必ず突き合わせること。
生年月日が合わない資料は使わない（この照合を怠って別人の記事を採る誤りが、
本プロジェクトで過去に実際に起きている）。

## 4. 盲検条件（守らないと holdout が holdout でなくなる）

判定中に**見てはいけないもの**:

- このリポジトリの分類器出力・最終採用ラベル
  （`pathway_*_labeled.csv`、`player_pathway_outcomes.csv`、`pooled_player_outcomes_*.csv`、
  各種 `*review_queue*.csv`、`data/manual/goldsets/`）
- 抽出の層（`gold_holdout_worksheet_key.csv`）。**層名は「2 つの測定源が食い違った行」であることを
  そのまま暴露する。**
- アウトカム（J1 到達・海外移籍・代表選出）
- もう一方の判定者の回答

ワークシートに `source_player_id` を載せていないのはこのためである。判定は
**ワークシートの氏名・生年月日・所属クラブと、外部の公開情報だけ**で行う。

## 5. 手順と分担

1. **パイロット 30 件**（`batch = pilot`）: 2 名で判定し、一致率・判定不能率・1 件あたりの
   所要時間を測る。ここで手順の穴が出たら**このプロトコルを直してから**先へ進む
   （判定済みの 30 件は破棄せず、プロトコル改訂の前後を記録する）。
2. **重要層 150 件**（`batch = important`）。
3. **中間チェックポイント**: ここまでの実測（層別の誤分類・判定不能率）で
   `gold_design_simulation.py` を再実行し、539 件で分解能が足りるかを確認する
   （SAP §6b-2b-ext。足りなければ拡張規則に従う。**アウトカムは見ない**）。
4. **残り 359 件**（`batch = rest`）。
5. **裁定**: 2 名の不一致行はユーザーが裁定する。加えて**一致行の 10% を点検**する
   （判定者 2 名の独立性が人間 2 名より弱いため、一致は独立性の証拠にならない）。
6. コーディネーターが機関名に §1b-4 の時点付き J 加盟規則を当て、gold カテゴリを確定する。

## 7. 運用（v2・パイロットの実測から）

- **1 件終えるごとにファイルへ追記する。** パイロット中に判定者 A が API エラーで 3 回落ちたが、
  追記済みの行は残った。まとめ書きにしていたら 7 件を失っていた。
- **5 件ずつ区切って進捗を報告する。** 長時間の連続実行は落ちる確率が上がる。
- 1 件あたりの目安は **4〜8 分**（パイロット実測の中央値: 判定者 B 4 分・判定者 A 8 分）。
  **公式ソースが見つからなければ深追いしない**——判定不能率そのものが測定対象である。
